# 海纳·运费对账
## 产品与技术设计／开发指引 v0.1.0

**把运输单、合同费率、承运商账单与履约凭证，核对成一份有依据、可复算、可复核的差异清单。**

文档日期：2026-09-19。产品工作名：海纳·运费对账；专家职称建议：物流运费对账专家。名称尚未由用户最终确认。工程代号：freight-reconciliation；与 Kiwi 的产品、版本、数据库和权限独立。

状态：开发基线提案＋同版设计交接包。不是已完成的生产软件，不是财务审计意见，不是对承运商多收费的认定。示例均为合成数据；本次没有取得真实客户合同、账单或既有对账代码，也没有完成 WorkBuddy 实机联调。

适用对象：产品负责人、物流业务负责人、对账专员、财务复核人、开发者和测试人员。

# 01　决策摘要：做什么，不做什么

## 1.1 唯一主任务

先做付款方视角的公路运输月度对账：货主或物流总包收到承运商账单后，导入本方运输台账、已确认合同费率、对方账单和履约凭证索引，系统解释每一笔费用应依据哪次运输、哪版规则、哪些证明，列出金额与证据差异，并跟踪人工复核结果。

首个工作单元固定为“一个经营主体＋一个承运商＋一个账期＋一个合同币种”。同一经营主体可建立多个案件，但不得把多承运商账目混在一次不分归属的运算中。本版以 CNY 为唯一币种。

结合用户已有固定线路、仓网运输和新能源重卡业务背景，建议先选固定起讫仓、明确车型、按实际车次结算的场景。此为优先验证假设，不意味着已经拿到客户订单或确认该模式最赚钱。车辆是否新能源不是对账公式，只有合同明确约定时才进入费率维度。

## 1.2 最小闭环

导入资料 → 确认字段与业务口径 → 确认合同规则 → 匹配实际运输 → 确定性重算 → 差异与缺证清单 → 人工复核与补证 → 新版重跑 → 冻结对账结果 → 导出沟通材料。

关键承诺：不漏行、不重复汇总、不用猜测补事实；相同已冻结输入和相同规则，产生相同的计算结果。

## 1.3 范围冻结

| 首版必须支持 | 明确不进入首版 |
| --- | --- |
| 固定线路、车型、按车次基础运费 | 零担重量／体积择大、复杂阶梯、公里浮动价 |
| 按明确到离场时间计算等候费 | 根据聊天推断等候时长、自动解释模糊合同 |
| 有合同条款及有效凭证的实报实销附加费 | 自动判断临时加价合理、保险理赔、违约罚款 |
| UTF-8 CSV、无宏 XLSX 结构化导入 | 任意扫描件全自动识别后直接结算 |
| 合同／签收 PDF、图片作为证据留存与人工定位 | 自动判定电子签名真伪、发票税务真实性 |
| 同车次多费用行，显式关联的当期冲销行 | 无分摊依据的“一行账单多车次”自动均摊 |
| 本地文件、单主体独立工作区、具名操作者 | 多租户云平台、完整 TMS／ERP／财务系统 |
| 待核金额、缺证、人工决定、导出记录 | 自动扣款、付款、开发票、改上游账、群发争议 |

复杂业务能被识别和排除，不等于被支持。未支持项必须出现在覆盖率与待处理清单中，不得从结果中消失。

# 02　产品价值与验证门槛

## 2.1 为什么不只是“直接问大模型”

模型适合解释列名、提出匹配候选、理解合同片段、起草补证问题。不可把几千行台账塞进上下文后要求模型凭记忆逐笔算账。产品应把事实、运算和人工决定保存在模型之外。

| 可重复交付能力 | 必须达到的实际差异 |
| --- | --- |
| 业务字段映射模板 | 同一承运商下个月可复用；列结构变化会告警 |
| 版本化合同规则 | 每笔费用指向具体条款、费率、生效日期和批准人 |
| 确定性金额与费用分组 | 逐分可复算；重复费与价差不会被计算两遍 |
| 双向完整性核查 | 账单未匹配、台账未见账单都显式呈现 |
| 证据定位与复核记录 | 从异常回到原文件／工作表／原始行／合同条款 |
| 重跑与版本差异 | 补证或改规则后显示哪些结论改变，旧审核不误用 |

已有成熟运输系统也将费用明细匹配与容差检查作为明确处理环节；Oracle 的官方资料说明了其发票行与运输成本匹配、偏差存储机制。[S05] 这证明功能范式并非空白市场，不证明用户有付费需求。切入点应是客户当前 Excel 作业里最费时、最容易返工的一小段。

## 2.2 前置验证，不以代码数量证明需求

先争取3家潜在客户提供脱敏样本，至少1家允许平行跑一个真实账期；这是投入门槛，不是统计学结论。首轮样本至少同时覆盖正常单、疑似重复、费率调整、缺签收、附加费和冲销。

必须记录：每月单量、实际人工耗时、可重复的计费模式、数据拿取难度、错账最终如何确认、决策人和付款人。没有完整台账时只能做“提供范围内检查”，不能承诺整月完整对账。

第一轮不把收费写死。优先验证固定范围的账期试用及模板配置服务，实际收费须先达成范围、验收和数据责任约定；不能按“AI标出的疑似金额”直接抽成。

# 03　用户、责任与五个验收场景

## 3.1 角色

对账操作者：导入文件、确认字段、提出关联、查看差异、补充来源；不自动获得付款权限。业务复核者：确认实际运输、额外服务、签收与等候事实。财务复核者：确认税口径、对账调整建议与结果版本。项目管理员：维护工作区、模板、规则及访问权限。

首版为具名单操作者工作区，可记录线下业务／财务复核附件；它不是多用户审批系统。外部人员的邮件或签字由用户上传后标记为“所提供的复核记录”，不能冒充已通过身份认证的在线批准。后续多人协同需单独实现身份与授权。

## 3.2 核心用户故事

| 编号 | 输入任务 | 验收输出 |
| --- | --- | --- |
| U01 | “把承运商9月账单与运输台账核对。” | 账单行完整分区、匹配结果、正反向遗漏提示 |
| U02 | “这条线路9月15日起调价。” | 按合同约定的计费时点选择费率，而非全月覆盖 |
| U03 | “为什么这次等待费多了50元？” | 到离场依据、免费时长、进位单位与公式 |
| U04 | “这里是补回的签收单。” | 新来源记录、新运行版本、受影响结果差异 |
| U05 | “生成发给承运商核对的材料。” | 脱敏差异表、逐项问题、依据定位与待证清单；不自动发送 |

## 3.3 成功输出的语言

推荐：“按当前已确认合同规则计算，账单金额高出100元，待承运商核对。”“该条费用缺少有效凭证，暂无法计算可比差额。”

禁止：“发现欺诈。”“已为你追回款项。”“全部正确，可以付款。”除非外部正式结果有可核验回执，也只能准确记录那一事件，不把对账过程升级为付款审批。

# 04　业务粒度：先搞清一笔费用是什么

## 4.1 四种编号不能混同

order_id 是客户委托；waybill_id 是运输单据；trip_id 是一次实际运输执行；bill_line_id 是承运商账单的一行费用。一车可以承接多个订单，同一车次也可以有基础费、等候费、过路费等多行账单。

本版基础计费对象为 trip。不得用“订单行数”替代“车次数”。同一 trip 对应多个订单时，基础运费只重算一次；订单与车次的明确关联来自台账或用户确认，不根据商品数量猜车次数。

## 4.2 核算组 ChargeGroup

核算组键：workspace_id＋carrier_id＋trip_id＋service_leg_id＋charge_code＋occurrence_id＋currency＋amount_basis。每一条已纳入账单行在一个运行版本中只能分配到一个组。基础费使用固定 occurrence_id=BASE；等候／实报费用按已确认事件编号分别建组。

service_leg_id 用于区分去程、回程及独立运输段。没有可靠区分时不得把同车同日的两次运输并为重复。单程线路与返程线路为不同 route_id；只有合同明确往返包价且有明确 trip 归属时才使用独立包价规则，首版暂不启用。

核算组是金额汇总的唯一粒度；异常可以一组多标签，但同一组的差额只能进入金额摘要一次。

## 4.3 拆单、合单、分批付款

一车多订单：保留关联表，不复制费用。一个订单分两车：必须有两个可靠 trip_id；不能依据账单双行直接认定两车真实完成。一条合计账单覆盖多车：要求承运商提供分项或业务方确认分配；首版列为 UNSUPPORTED_AGGREGATION，不均分。

分批付款是支付安排，不代表基础运费应计多次；本产品不以付款笔数构造运输次数。已付信息仅作补充证据，不参与自动消除当期差异。

# 05　数据输入与原文证据

## 5.1 六类输入

| 类型 | 最少需要的事实 | 缺失时如何处理 |
| --- | --- | --- |
| 运输执行台账 | trip、承运商、线路、车型、实际出发、执行状态 | 未执行／无明确运输的费用不自动通过 |
| 承运商账单 | 原始行、业务引用、费用类型、币种、金额、口径 | 保留整行及问题，计入不可比部分 |
| 合同费率表 | 范围、计费时点、生效区间、金额、条款定位 | 未确认规则不正式计算差异 |
| 签收／履约索引 | trip、凭证文件、状态、核对人、定位 | 缺签收不等于运输不存在，也不等于应付为零 |
| 附加费事件 | 事件编号、时长或票据、条款、有效性 | 无凭证保留 billed，expected/delta=null |
| 别名与字段映射 | 承运商、线路、车型、费用代码映射 | 模型候选由人确认后复用 |

合同原 PDF／图片可以作为证据文件；首版依赖人审定的结构化费率表。可选文本提取只提出规则草稿，不能把“模型看懂了合同”当生效规则。扫描件 OCR 不是核心前置；后续启用必须人工核对计费数字、单位、否定词和日期。

## 5.2 原始来源不可丢

每个来源保存 asset_id、原始文件名、SHA-256、导入时间、文件类型、字节数、主体范围和解析器版本。CSV/XLSX 的定位包含原工作表、原行号、原列名／单元格地址；行号从文件第一行起算，不能因去除表头后重排而变化。

PDF／图片证据保存页码（对人1起算）、原图或文件引用与人工批注区域。来源哈希仅证明本系统保存内容的一致性，不证明文件真实、签名有效或司法证据效力。

归一化值必须保留 raw_value、normalized_value、normalization_rule、source_locator、confirmation_ref。展示用别名不能覆盖原始承运商或线路名称。

# 06　导入、字段映射与完整性控制

## 6.1 安全读取顺序

先校验后缀与文件头、压缩展开上限、文件大小和是否加密；再枚举全部工作表及隐藏行列；再识别表头、明细、合计、说明行；最终由人确认导入范围。隐藏行不能默认跳过，用户可排除但必须有行号、原因和金额去向。

首版建议限制：每文件25MB、每案件10个结构化文件、每文件5万明细行、单案件10万账单行；这是待压测的配置目标，不是已经实测的性能。超限明确拒绝或转分批，不静默截断。

无宏 XLSX 允许作为输入；XLS/XLSM、外部数据连接、加密文件默认拒绝。公式字段不得直接运行：核心金额若来自公式，只能用已存在的缓存值并显式标注缓存来源，由用户提供并确认值化版本；无缓存或来源不明阻断正式运行。下游导出不能执行来自原文件的公式。[S08]

## 6.2 映射确认

先读取列名和脱敏样例，模型提出字段候选；映射页显示原列→目标字段、单位、税口径、时间格式、ID字符串规则。关键列不得凭置信度自动启用。ID保留前导零；科学计数法导致的长编号信息丢失不可逆，要求原始文本版。

模板按经营主体、承运商、表结构签名和版本存储。增加列可以告知后复用；关键列改名、类型变化、金额单位变化必须重新确认。一个“金额”列是元还是分、含税还是未税，必须分别确认。

## 6.3 控制总数与控制金额

账单明细必须互斥分入：可比已分组、不可比／待匹配、明确不属本案件。合计行不当明细，仍用于控制额。负数冲销保留符号，不取绝对值参与应付合计。

source_detail_signed_total = comparable_billed_total + unresolved_billed_total + out_of_scope_billed_total。

账单声明合计与明细和不相等，显示 SOURCE_TOTAL_MISMATCH；无法读取金额的行没有资格被计为零。存在解析失败金额时，总金额完整性为 false，摘要不得展示“全账期已对平”。同样保存源行数、被识别明细数、排除行及失败行列表。

# 07　匹配引擎：强关联优先，模糊只作建议

## 7.1 确定性匹配顺序

P1：承运商作用域内，可靠 trip_id／双方共同运单号完全一致，且线路、执行日期与费用事件无冲突。

P2：双方维护过的别名或编号映射，且唯一命中；映射必须有确认记录。

P3：路线、车型、日期窗口、车辆脱敏键、费用类型组合产生候选，仅建议。任何多候选、硬字段冲突、仅金额相近，都不自动绑定。

排序分数不是事实证据。首版只自动接受P1/P2且一致性通过的关联；P3必须由人在管理页选定、确认该行金额分配，并写入决定版本。

## 7.2 匹配状态

EXACT、CONFIRMED、AMBIGUOUS、UNMATCHED、CONFLICT、OUT_OF_SCOPE（前两项分别表示强匹配与人工确认）。状态与金额比较状态分离：能匹配到运输不代表已找到正确费率；有价差不代表履约凭证齐全。

同一个 bill_line_id 不得被多个组消费。分组后若账单原金额不守恒，整个运行不得进入可冻结状态。

## 7.3 双向遗漏与跨期

账单→台账：未找到运输，显示待查执行记录。台账→账单：已执行却未出现在所提供账单，显示 NOT_BILLED_IN_PROVIDED_SCOPE，不默认应付缺漏或节省金额。

账期默认按合同约定的实际出发时点选择费率；对账账期与开票时间分开。迟到票据、跨月补账必须保留原 service_time，不能按本月新价格重算上月运输。

历史疑似重复仅在用户导入并明确范围的历史台账中检查，必须展示 history_coverage_from/to。历史范围不明不说“已排除历史重复”；跨期款项不自动跨期净额冲销。

# 08　合同规则模型与生效控制

## 8.1 一个规则只表达可执行的明确约定

RateRule包括 rule_id/version、合同文件定位、承运商、route_id、vehicle_class、charge_code、amount_basis、CNY、生效起止时间、计费时点选择、公式类型、参数和确认记录。

effective_from包含、effective_to不包含；统一保存带时区的ISO时间，业务展示默认Asia/Shanghai，与使用者设备时区无关。合同写“9月15日起”时，需人工明确该日00:00所用业务时区。没有时区或时点定义不自动猜。

## 8.2 选择与冲突

候选规则先按主体和承运商、路线／车型、费用类型、服务发生时点过滤，再应用已明确批准的例外规则。首版不设“更晚文件自动覆盖一切”的隐式优先级。

同一适用条件同时命中两条生效规则而无明确替代关系：RATE_AMBIGUOUS，expected与delta为空。找不到规则：RATE_NOT_FOUND。中途调价必须保留旧规则并设置非重叠区间，不回写旧费率。

## 8.3 人工确认不是聊天中的一句“好”

规则草稿可由模型生成；生效需要管理页展示来源、字段、公式、日期和适用范围，具名用户对规则摘要确认。确认绑定workspace、actor、rule_digest、source_digest和version。后续任何参数变化生成新版本并失效相关运行，不复用旧批准。

规则不采用eval、动态Python表达式或任意SQL；使用封闭枚举PER_TRIP、WAIT_BLOCKS、ACTUAL_RECEIPT。未支持条款返回unsupported，并列出需要补充的规则维度。

# 09　精确计价：三种首版费用

## 9.1 共同数值规范

货币金额在核心契约中均为整数“分”，允许账单冲销行为负数。单值绝对值不超过10^12分；组与案件汇总也检查上限。布尔值不是整数输入；NaN、Infinity、二进制浮点金额、格式不明字符串不得进入核心。

导入元金额用十进制字符串严格转分，不用float乘100。超过两位小数默认阻断，除非合同明确更高精度单位价及舍入方式；本版不支持该扩展。Python Decimal支持十进制精确表达与可指定舍入，适合边界转换；核心求和仍采用整数。[S06]

含税／未税必须同口径比较。首版不自动推税率、不把含税价格除以猜测税率。合同与账单口径不同则BASIS_MISMATCH，等待用户提供经确认的同口径金额。示例中的GROSS仅是“已声明含税金额”，不表明税率或税务资格。不同账单口径必须分栏汇总，不输出混合净额；参考批次要求全部账单同一口径。

## 9.2 基础运费 PER_TRIP

expected_minor = rate_minor × verified_trip_units。首版每个trip/leg基础核算组的verified_trip_units固定1，不能用账单自报数量放大。一个多车合计必须先拆为可验证的多个trip，否则不计算。

基础费数量、车型及路线必须由实际执行证据支撑。未发车、取消、改线或返程费用不按原规则自动等同处理，列入特定人工复核。

## 9.3 等候费 WAIT_BLOCKS

以带时区的到离场时间计算整数秒elapsed_seconds。确认free_seconds、block_seconds和price_per_block_minor；合同若规定不足一个单位进一，采用：billable = max(0, elapsed − free)；blocks = (billable + block − 1) // block；expected = blocks × price_per_block_minor。

不先把秒数截断成小时或分钟。离场早于到场、缺时间、重叠事件、重复计算同一等待区间都阻断。装货等待与卸货等待是不同occurrence_id；是否共用免费时间由合同规则决定，首版只支持每事件独立免费时间。

示例：在场180分钟，免费120分钟，每30分钟50元，预期100元；账单150元，差额＋50元。恰好免费120分钟则0；多1秒且合同按块进位则1块，不由模型按“差不多”四舍五入。

## 9.4 实报实销 ACTUAL_RECEIPT

仅在已确认合同允许该费用且凭证有效、归属明确时，expected为对应已核验凭证金额之和。receipt_id/content_digest防止同一票据重复分摊；跨车次拆票或分摊进入后续版本。

可配置明确上限：expected=min(valid_receipt_total, cap_minor)。无票据不是0元，应为expected=null并提示MISSING_RECEIPT。合同明确某附加费已包含在基础费中且证据充分时，才可使用已确认的“不另收费”规则判断，首版参考算例不替业务人员自动作此解释。

# 10　重复计费、冲销与金额去重

## 10.1 两种重复必须分开

文件重复导入：同一案件、来源类别与内容摘要相同，应返回原asset/import结果，不生成第二份账单。这是技术幂等。

业务疑似重复：不同账单行落到同一trip/leg/charge/occurrence，但规则仅允许收取一次。仍保留所有原始行，在核算组层求账单净额与一次预期额，标记DUPLICATE_SUSPECT，由人核对是否有遗漏的独立运输或费用事件。

同金额、同日、同车牌不是充分重复证据。不能自动删除“看起来重复”的行，也不能分别将“重复金额”和“高报金额”加进总风险额。

## 10.2 首版冲销范围

支持同案件内、同核算组、显式reversal_of_bill_line_id的部分或全部冲销。被冲销行必须存在且为正数；币种和金额口径相同；同一原行的累计冲销绝对值不得超过原行金额；不允许冲销指向另一条冲销。

原行1200元、冲销−100元、合同1100元：账单净额1100元，可比差额0；保留两行和关联，不把−100元当异常漏计。孤立负数、跨期调整、超额冲销或缺原行：不可比，等待补充而非自动净额抵消。

## 10.3 金额唯一归集

delta_group = billed_net_group − expected_group，仅expected确定且口径一致时存在。positive_difference=sum(max(delta,0))；negative_difference=sum(min(delta,0))；net_difference=positive+negative。

异常条目引用group_id；汇总按group_id而非issue_id。疑似重复1500元同时被标金额偏高，正向待核金额仍为1500元，不能报3000元。缺证金额单列“不可比账单金额”，不可加入已计算价差。

# 11　异常规则库与证据等级

## 11.1 首版规则目录

| 规则码 | 检查内容 | 处理方式 |
| --- | --- | --- |
| SOURCE_TOTAL_MISMATCH | 明细和与声明合计不符 | 案件完整性阻断 |
| PARSE_FAILED／ID_DAMAGED | 必需字段解析失败、编号损坏 | 保留原行并阻断相关计算 |
| UNMATCHED／AMBIGUOUS | 无运输关联或多个候选 | 人工匹配，不猜选 |
| CARRIER_CONFLICT | 主体或承运商不一致 | 隔离，禁止跨主体匹配 |
| RATE_NOT_FOUND／RATE_AMBIGUOUS | 费率缺失或重叠 | expected/delta=null |
| BASIS_MISMATCH | 含税／未税等金额口径不一致 | 暂不比较 |
| AMOUNT_HIGH／AMOUNT_LOW | 可比组存在正／负差额 | 展示公式与依据 |
| DUPLICATE_SUSPECT | 同计费对象疑似多收一次 | 不删行，组差额只计一次 |
| MISSING_POD／POD_CONFLICT | 履约凭证缺失／矛盾 | 算术可保留，证据状态不通过 |
| MISSING_RECEIPT | 实报费用无有效证明 | 不把应计金额设零 |
| WAIT_EVIDENCE_INVALID | 时间缺失、倒置、区间冲突 | 不重算等候费 |
| REVERSAL_INVALID | 原行缺失、跨组、超额冲销 | 保留原负数，阻断该组 |
| HISTORICAL_DUPLICATE_CANDIDATE | 所提供历史中疑似重复 | 标明历史覆盖与待核条件 |
| NOT_BILLED_IN_PROVIDED_SCOPE | 已执行运输未见于所给账单 | 提醒跨期确认，不算节省 |
| UNSUPPORTED／OUT_OF_SCOPE | 超出首版或案件范围 | 显式排除，计入覆盖缺口 |

## 11.2 三个正交维度

comparison_status：COMPARABLE／NOT_COMPARABLE；evidence_status：COMPLETE／MISSING／CONFLICT；review_status：OPEN／CONFIRMED_DIFFERENCE／ACCEPTED_AS_BILLED／NEEDS_EVIDENCE／DISPUTED／OUT_OF_SCOPE／STALE。

金额0且缺签收不能显示“对账通过”。差额为正且模型置信度很高，仍不能显示“多收已确认”。默认显示“核算一致”“待核差异”“缺证”“待人工关联”等中性标签。

## 11.3 单条异常最少证据

须包含原账单定位、运输定位、费率或凭证定位、采用公式、账单值、应计值或null、差额或null、规则版本、判断原因、缺失信息、下一步、责任角色和运行版本。字段不可得写不可得；模型补写不存在页码属于验收失败。

# 12　端到端流程与人工决定

## 12.1 流程

A建案：确定主体、承运商、币种、账期边界、台账与历史覆盖范围。

B导入：登记来源、字段映射预览、行数金额控制、解析异常；人确认使用范围。

C规则：从确认费率表构建规则草稿，核对来源、生效区间与公式，人审后生效。

D匹配：确定性匹配与候选队列；人确认模糊关联，不回写原文件。

E运行：冻结input_manifest、mapping、rule_bundle与matching_decisions，产生run_id；逐组计算、规则检查和覆盖摘要。

F复核：在“原账单＋执行事实＋合同／凭证＋计算轨迹”四栏视图判断，补证或提更正，不直接编辑已算出的差额。

G重跑：新增事实或规则产生新run，比较新增／消失／金额变化的异常；旧人工决定只有摘要完全一致时可标仍适用，否则STALE。

H冻结与导出：具名用户确认当前运行和结论，生成冻结版本及固定文件。导出是提供核对材料，不是付款指令。承运商沟通仍由人发送。

## 12.2 确认的边界

聊天中的“可以”“都批准”不能作为批量抹平异常的凭据。模型只能prepare_mapping、prepare_rule、prepare_match、prepare_decision、prepare_freeze。最终activate/confirm在认证管理页执行并绑定对象摘要。

用户接受原账单金额时保留原始计算差异、接受理由及附件，并另外记录处理决定；不修改expected伪装从未有差异。复核也不能把不存在的来源补成“已验证”。

# 13　领域模型与候选数据契约

同版02_contracts目录提供8份候选JSON Schema。它们是增量实现的接口基线，非既有产品接口，也不覆盖生产系统的全部内部表。01_design/data-dictionary.md补充完整字段关系。

| 契约 | 作用 | 必须维持的关系 |
| --- | --- | --- |
| SourceAsset | 原始文件与证据定位范围 | 摘要、范围与解析版本固定 |
| MappingProfile | 可复用字段映射 | 类型／单位／口径有确认记录 |
| RateRule | 可执行合同条款 | 已确认、版本化、明确生效区间 |

每个workspace独立隔离。workspace_id属于服务端认证上下文，不接受模型通过工具参数自行选租户；持久化契约包含它不等于工具允许任意传入。

业务日期用ISO 8601含偏移量。所有引用使用稳定ID和版本；展示名称可以修改，但不改变历史关联。存储对象的schema_version固定，升级用迁移器而非静默猜兼容。

以下全部是合成数据，不是用户实际费率、真实欠款或适用税率。表中金额单位为元；底层算例为整数分。全部账单数据均属于同一示例案件，税口径一致者才可比。

| 组 | 场景 | 账单净额 | 规则应计 | 可比差额 | 结论 |
| --- | --- | --- | --- | --- | --- |
| G01 | 正常基础费 | 1,000 | 1,000 | 0 | 金额一致、证据完整 |
| G02 | 基础费高报 | 1,300 | 1,200 | +100 | 待核金额差异 |
| G03 | 等候费 | 150 | 100 | +50 | 展示时长与块数 |
| G04 | 同一基础费两行 | 3,000 | 1,500 | +1,500 | 疑似重复与偏高，同组仅计一次 |
| G05 | 过路费缺票据 | 80 | 不可得 | 不可得 | 不可比金额80 |
| G06 | 账单低于规则 | 1,050 | 1,100 | −50 | 反向差异，不能与正向混淆 |
| G07 | 金额口径冲突 | 990 | 不可比 | 不可得 | 不可比金额990 |
| G08 | 金额一致、缺签收 | 1,250 | 1,250 | 0 | 算术一致但证据不完整 |
| G09 | 1,200减100冲销 | 1,100 | 1,100 | 0 | 两行有显式关联 |
| G10 | 未找到运输 | 700 | 不可得 | 不可得 | 待匹配金额700 |

账单12行，10组。账单净额10,620元。可比组账单8,850元、应计7,250元；正向差额1,650元，反向差额−50元，净差额1,600元。不可比账单净额1,770元；8,850＋1,770＝10,620，守恒成立。

可比组7/10，但组数不是账单行覆盖。可比账单行9/12＝75%。金额覆盖使用绝对账单行金额避免冲销掩盖：9,050／10,820≈83.64%。有缺签收的G08仍计入“金额可比”，但不能计入“证据完整且待核项为零”。所有覆盖指标同时展示分母与范围。

这些是参考引擎的固定金标，不是生产系统验收结果。04_reference只实现规范化组的算术和有限规则，不负责真实文件导入、签收识别、权限、任务恢复或Excel输出。

# 16　状态、幂等、事务与恢复

## 16.1 分离状态域

Case：DRAFT→READY→RUNNING→REVIEW_REQUIRED→FROZEN→ARCHIVED。Job：QUEUED／RUNNING／SUCCEEDED／PARTIAL／FAILED／CANCELLED。Source/Rule/Mapping：DRAFT／CONFIRMED／SUPERSEDED。Review独立保留OPEN等状态；Export记录PREPARED／RELEASED／DOWNLOADED。

PARTIAL表示有限范围已完成但仍有失败项，不可伪装SUCCEEDED_COMPLETE。FROZEN只是用户冻结当前结果，可带明确未解决项，不意味着全额同意或付款。冻结包首页必须显示未解决金额、数量和覆盖缺口。原始金额解析不全、源合计不平或行归属不守恒时，只能导出草稿，不能正式冻结；金额已知但应计未确定的待核组可以保留在冻结清单中。

## 16.2 版本和幂等

case_revision、rule_bundle_version、mapping_version、matching_version、run_id分别管理。输入变化不修改旧run；新run关联supersedes_run_id。计算结果摘要不含当前时间，避免同一输入仅因生成时间不同而算不同结果；事件时间另存。

变更请求使用workspace＋operation＋idempotency_key唯一索引并绑定request_digest。同键同内容返回原结果；同键不同内容返回IDEMPOTENCY_CONFLICT，不自动生成另一把键。先保存job与输入摘要，再开始耗时处理；客户端超时后查询job，不盲目重发。

## 16.3 数据库与产物

新增表：cases、assets、source_rows、mapping_versions、trips、bill_lines、evidence_links、rate_rules、match_assignments、runs、charge_groups、results、issues、review_decisions、jobs、exports、audit_events。

关键约束：run_id＋bill_line_id唯一归属；rule引用固定版本；result不可更新；decision/result_digest绑定；导出清单只引用一版run。以单机SQLite事务写入一致结果和状态；WAL不能放在网络共享文件系统上。[S07]

文件写到同卷私有staging，完成hash后原子rename；数据库事务再发布manifest引用。失败留下未引用staging可回收，不暴露半成品。数据库与文件不是一个天然跨资源事务，必须实现恢复扫描和完整性校验。

重启后RUNNING转RECOVERY_REQUIRED并按检查点恢复；没有证明幂等的外部动作不重放。本版没有外部付款／发送。备份采用数据库一致性快照并包含被引用文件，恢复核对hash和run控制总数；不能只复制主db忽略WAL而声称完整。

管理页确认路由与MCP工具分离：/admin/confirmations/{id}/confirm、/admin/exports/{id}/release。GET无副作用，模型不可调用最终确认端点。开发CLI仅提供管理辅助且使用同一权限检查，不能成为绕过通道。

## 17.2 权限

file_read_selected、case_write、rule_prepare、run_execute、evidence_read_redacted、review_prepare、export_prepare为操作能力；rule_activate、review_confirm、export_release由可信人类操作控制。工具annotation只提供提示，不构成授权或网络隔离保证。[S09]

单机模式认证主体来自用户启动的受限工作区会话；管理页用独立会话、CSRF、Origin检查和一次性确认凭证。远程企业版后续采用HTTPS和适当OAuth，但不能直接把本地固定用户ID搬成共享服务器全体用户。

# 18　WorkBuddy落地：先专家，再工作台

## 18.1 产品形态

先发布一个专家，内部三项技能：freight-intake-and-rules（导入与口径确认）、freight-reconcile-and-explain（匹配、运行和解释）、freight-review-and-export（补证复核与结果导出）。不是三个互相独立收费的“专家”，也不是多Agent团队。

官方专家文档支持声明MCP／已上架连接器依赖；技能结构允许references/scripts/templates，适合把知识引导与确定性实现分开。[S01][S02] 本包三项技能仅为流程草稿，不包含完整平台资产、市场ID或可运行生产MCP。

## 18.2 接入路线

M0用CLI或本地管理页验证Core；M4开发一个本地stdio MCP连接器，专家依赖该连接器。CLI仅作同一Core的开发／回归入口，不在同一个平台连接器里同时混装CLI和MCP两种接入方式。

官方连接器文档允许本地stdio，远程HTTPS SSE或streamableHttp；一个连接器只配置一个MCP Server，单次请求建议30秒内响应。[S03] 因此导入／重算统一返回job_id，客户端按用户操作轮询。此为产品内任务机制，不代表本次助手会后台执行任务。

依赖安装、相对路径、打包后的资源位置、文件选择句柄、Windows路径、WorkBuddy重启恢复、超时、权限提示、输出文件展示，均必须实机验证。不可假设技能附带Python就一定在客户电脑安装成功。

## 18.3 Buddy后置

当真实客户反复使用同一案件、需要常驻差异列表与历史版本时，再将同一专家和Core封装成Buddy应用，提供“开始本期对账／查看待补证／比较新版／导出核对材料”等入口。官方Buddy应用可组织工作模式、场景、专家、技能和连接器。[S04]

本地stdio在完整Buddy中的首次绑定、内嵌UI及授权组合必须另行测试；官方文档对内置连接器与跳过首次绑定有不同场景描述，不能凭开关推断所有组合已支持。首版不因Buddy界面需要就上云或放宽私密文件访问。

# 19　界面与导出设计

## 19.1 五个页面

案件首页：显示账期、主体、承运商、数据覆盖和版本，不先给“节省金额”大字。

导入与映射页：左右对照原列和目标字段，展示合计控制、排除行、未知口径与确认动作。

差异工作台：金额差异、缺证、待匹配、规则冲突分区；默认按用户定义严重性和可核金额排序，不把不可比金额混入差额榜。

证据复核页：左原账单，中运输／凭证，右规则与公式，下方决定、理由和附加证据；人工关联或规则改动明显标识。

版本与导出页：展示本轮较上轮新增／消失／变化、失效决定、未解决项；确认后输出冻结版本。

## 19.2 输出文件

首版交付结果XLSX＋Markdown说明，PDF可作为后续固定版式导出。结果工作簿包含：总览、逐行台账、核算组、待核差异、待补证、待匹配、规则引用、复核记录、版本变化、来源清单。

正式结果值由Core生成，文件为只读业务快照；导出的公式不得被当作真值源。可选复算页使用固定安全公式且与Core结果比较，不读取原账单中的可执行公式。机器复算以同版JSON和参考规则为准。

列至少含原账单行、trip、费用、账单金额、应计／null、差额／null、口径、证据状态、原因、来源定位、处理人、决定、run_id。未知数值留空并在状态列解释，不能用0或字符串“0”替代。

## 19.3 对外材料与隐私

默认外发投影仅包含相关承运商的费用行、必要运输引用、条款摘录和问题。不得包含其他承运商报价、成本底线、司机完整身份证／电话、无关客户资料或系统路径。原始证据不默认整包附加，用户明确选择后生成清单与摘要。

对外沟通稿用“请协助核对／请补充依据”，不写“已确认欺诈”。导出后只记录DOWNLOADED，用户自述已发送单独标注REPORTED_SENT；没有真实渠道回执不显示“已送达”。

# 20　数据保护与安全威胁模型

## 20.1 本地存储不等于全部处理本地

原文件、规则和算术默认留在本地Core；WorkBuddy所用模型可能在远程处理工具返回内容。模式A仅返回脱敏列名、候选与最少片段；模式B经用户授权才扩大数据；禁止宣称“绝不出本机”，除非模型及全部链路均有实测证明。

客户资料授权与保存期限由实际合同、企业制度和适用要求确定，不能设置一个通用期限就声称合规。试点默认最小化采集，不请求个人证件、银行账户或驾驶员全量轨迹。

## 20.2 必测风险

| 风险 | 强制措施 |
| --- | --- |
| 提示词注入 | 文件／合同文字只作数据，不执行其工具指令 |
| 任意文件读取 | 文件选择授权＋工作区路径白名单，拒绝越界及符号链接逃逸 |
| 压缩炸弹／超大表 | 展开大小、单元格数量、时间与内存限额 |
| 宏／公式注入 | 不执行宏、不跟外链；外发文本强制文本类型或转义 [S08] |
| 同主体多案件混算 | 每查询带服务端workspace/case隔离；行归属唯一 |
| 模型自批 | prepare与confirm隔离；一次性凭证不进模型上下文 |
| 越权导出 | 授权范围＋脱敏投影＋版本摘要绑定 |
| 日志泄露 | 不记录原始整表、凭据、联系方式；结构化错误码 |
| 哈希伪安全 | 哈希只保一致性，不代替鉴权或文件真实性核验 |

## 20.3 威胁边界

同一台机器若用户或恶意程序拥有全盘管理员权限，无法仅靠应用保证原始库不被篡改。首版提供可追溯与完整性检查，不承诺司法级不可抵赖账本。后续企业版若需强审计，单独设计身份、签名、集中审计与保留策略。

# 21　质量指标、日志与运维

## 21.1 正确性优先于“自动通过率”

账单行归属守恒100%；可解析金额守恒精确到分；相同输入重算一致；未知值不归零；任意关键金额、合同日期、单位和关联不得仅由模型未确认建议决定。这些是上线硬门槛，不是宣传目标。

建议性能验收：在指定8GB内存测试机上，1万账单行＋1万运输记录，在不调用模型且已配置模板的情况下60秒内完成主要匹配和核算，单工具受理3秒内返回job_id。实际耗时、CPU与峰值内存必须记录，不将目标写成实测。

## 21.2 可观察性

事件记录import_started/completed、mapping_prepared/confirmed、rule_activated、run_started/completed、issue_created、decision_confirmed/stale、export_released/downloaded。携带trace_id、case_id、run_id、版本与数量，不带整条隐私数据。

指标：导入失败率、未匹配行比例、规则冲突数、证据缺口率、金额覆盖、人工干预次数、单案件净耗时、人工误报确认率。差异金额不是收入，已接受的对账调整也不是追回现金。

## 21.3 故障和恢复

源文件损坏：隔离来源，不继续假装完整。磁盘满：停止发布、保留失败清单。规则版本失效：旧结果只读，新run重算。模型不可用：已确认模板与规则仍能完成确定性处理；解释可退化为固定模板。WorkBuddy关闭：Core已保存案件可用管理页／CLI继续读取。

# 23　验收体系与测试样本

同版05_tests/acceptance.csv列出80项系统验收规格，初始全部NOT_RUN。参考包自检另行记录，只证明候选契约、合成算例与参考实现一致，不替代这些系统验收。

测试分层：纯算术金标、来源／关联不变量、错误分支、文件解析集成、事务故障注入、权限与导出安全、WorkBuddy实机、真实客户盲审。任何一层没有执行应明确保留NOT_RUN，不将设计评审或自检当通过证明。

## 23.1 必须覆盖的性质

账单行顺序变化不改变结果；重复导入同一来源不增加账单金额；拆成两个输入文件仍保持同一账单行归属；不同案件相同文本不误去重；新增一条独立合法费用不改变其他组；更换费率版本仅影响适用组；删除证据不能把未知变为通过；净额0不掩盖正负差异。

金额相关必须测试免费边界、跨秒进位、负数冲销、超限、布尔输入、浮点拒绝、税口径不一致；规则测试起止边界、重叠、缺失、时区和跨月服务时间。

## 23.2 真实金标

至少由业务人员和财务人员对同一批样本独立标注再裁定冲突；“所有账单行”是总体分母，不能只用模型发现的异常作为验收集。记录正常与各异常类数量、确认标签、来源和不能裁定的项。

模型版本、提示词版本及配置在每轮对照中冻结；同一数据不能一边调参一边报告最终测试成绩。模板构建样本与留出验证样本分离，小样本结论不外推整行业。

# 24　试点设计、商业验收与停止条件

比较三种方式：现有人工Excel流程；原生WorkBuddy／通用模型处理同样获准材料；本产品。时间包含材料准备、模板配置、核验、误报处理和返工，不能只比较模型生成时间。

建议试点通过线：同一人员配对任务的中位净耗时减少30%以上，全部高风险金额与归属错误在已裁定样本中无漏报；人工确认的金额异常准确率至少95%，并报告样本数和不确定性。以上为投入决策目标，尚无实测，不是性能或收益承诺。

首个账期单独计入配置成本；第二个账期验证是否复用模板、是否仍愿意使用、是否愿意付费。收益以用户确认的时间节省和实际被双方认可的调整分开记录，不能把所有待核差异宣传成追回资金。

停止或改范围：拿不到完整授权样本；每家费用结构都需独立大改且不可复用；多数时间花在无法取得的凭证而非系统能改进的核对；与原生WorkBuddy对比无净收益；客户现有TMS已稳定覆盖且无迁移理由。停止新增功能不等于丢失已有客户资料，必须提供可读导出。

## 26.3 M0仍须解决

真实客户的计费对象究竟是车次、趟次、运单或吨公里；免费等待是否共用；调价依据哪个业务日期；应以什么凭证确认履约；账单中的冲销如何标识；数据来自哪些系统；合同和历史覆盖是否完整；本地运行环境与WorkBuddy文件权限是否满足；业务与财务复核责任如何落地。

这些事项不需要等答案才能写原型，但在未确认前，只能使用合成数据和未生效规则。首个可收费交付应是一个明确账期的可核查成果，而不是“万能物流专家”的人设。
